# Expedient Employment Architecture

## Runtime boundaries

Expedient Employment 2.0 has five main runtime layers.

1. The React renderer displays jobs, applications, assistant conversations, workflows, schedules, and service status.
2. The context-isolated preload exposes a fixed set of methods. It does not expose Node.js, filesystem access, arbitrary IPC, or the control-service token.
3. The Electron main process validates renderer arguments, owns child processes, applies the webview policy, and maps each method to a fixed backend route.
4. The Python control service binds to loopback on a random port and requires a random bearer token generated by the main process.
5. Python domain modules own storage, tools, assistant state, workflows, schedules, and the recruiting pipeline.

```text
React page
  -> fixed preload method
  -> validated IPC handler
  -> authenticated loopback route
  -> domain service
  -> SQLite, local files, or bounded subprocess
```

## Control service

`job_pipeline/service.py` is deliberately small. Its request body cap, route table, identifier checks, and loopback binding are part of the security boundary. Routes are versioned under `/v1`. Unknown routes and methods fail closed.

The Electron owner in `gui/electron/control-service.cjs`:

- generates the bearer token;
- starts Python with an explicit project root and data root;
- parses one structured readiness event;
- keeps the token in the main process;
- caps response sizes and timeouts;
- stops only the child process it owns.

## Tool broker

`job_pipeline/tool_broker.py` is the only assistant and workflow execution gateway. Each tool definition includes:

- a stable name and description;
- JSON Schema input and output contracts;
- one policy class;
- timeout and output limits;
- a handler that receives a cancellation signal.

Policy classes are `read`, `local_write`, `external_draft`, and `external_action`. External actions require an approval digest bound to the exact tool name and normalized arguments. The scheduler does not accept external-action tools.

Audit records contain lifecycle state, duration, policy, hashes, sizes, and error classes. They do not contain prompts, page contents, credentials, resumes, or tool output bodies.

## only-cli adapter

`job_pipeline/integrations/only_cli.py` translates typed broker calls into a fixed command catalog. It does not accept arbitrary executable names or shell fragments. It uses argument arrays, bounded timeouts, output caps, an application-owned state directory, and standard input for session material.

The runtime is pinned under `gui/only-cli-runtime`. Installation omits optional dependencies, which excludes the optional fingerprint-impersonation transport. The packaged application contains only the reviewed runtime closure.

## Web intelligence and workflows

`job_pipeline/web_intelligence.py` implements public-page fetching with:

- HTTP and HTTPS scheme validation;
- rejection of URL user information;
- all-answer DNS classification;
- global-address requirements;
- peer-address pin verification;
- redirect revalidation;
- response and MIME caps;
- bounded parsing and crawl limits;
- cache controls and challenge signals.

`job_pipeline/web_workflows.py` adds validated DAG execution. Nodes can depend on earlier nodes and interpolate exact prior results. The engine supports dry runs, retries, resume state, cancellation, circuit controls, and structured datasets.

These are original MIT modules. They provide the useful orchestration and data-extraction behavior requested from restricted-license products without incorporating their source or internal structures.

## Assistant

`job_pipeline/assistant.py` persists conversations, messages, queue state, attachments, tool events, and retry relationships. Provider adapters receive bounded message history and the broker's tool schemas. A completion loop is capped at eight tool rounds.

Image bytes remain local by default. Sharing an attachment with a configured provider requires the request's explicit image-upload flag. Attachments are content-addressed and bounded by type, count, and size.

## Scheduler

`job_pipeline/scheduler.py` stores interval and timezone-aware daily schedules. Work claims use leases so overlapping wakeups cannot run the same schedule concurrently. Missed intervals are coalesced instead of replayed in an unbounded burst.

`job_pipeline/scheduler_cli.py` runs due work headlessly. `scripts/install-scheduler.ps1` creates a per-user, hidden, limited-privilege Windows task with an IgnoreNew overlap policy.

## Recruiting pipeline

The pipeline keeps discovery, validation, verification, scoring, and application preparation separate. A job must pass role, geography, freshness, duplicate, and application-page gates before it reaches the ranked shortlist. Application state and user outcomes are stored independently from a new discovery run.

`job_pipeline/recruiting_acceptance.py` provides the deterministic high-volume release gate. It uses synthetic fixtures only and exercises the complete validation, deduplication, scoring, and SQLite ranking path.

## Packaging

Electron Builder assembles the renderer, Electron code, Python package, scripts, public configuration, documentation, license files, and reviewed only-cli runtime. Local configuration overrides, caches, reports, databases, credentials, and user attachments are excluded.

Inno Setup creates a per-user Windows installer and Start Menu shortcut. The package build and installed-artifact smoke test are release requirements.
